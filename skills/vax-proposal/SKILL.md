# 입찰 제안 하네스 (재료 팩 → 게이트 → 초안 → HTML → Figma)

대표의 `/bid-loop`(P1~P6 게이트 · `_STATE.md` 상태 기계 · 심사 루브릭)를 뼈대로 삼고, 서버가 하던
「전략·서술 쓰기」(방향 → 전략 → 절별 서술)를 P3와 P4 사이에 넣었다. 회사 팩트·실적·인증·숫자는
**재료 팩에 있는 것만** 쓴다. 없으면 만들지 않고 `⚠️ 확인필요`로 남긴다. 제안서 문장은 그대로
발주처에 가므로 추측이 가장 비싸다.

## 언제 쓰나
- "R26BK0123 제안 진행해줘", "이 공고 가점 진단부터", "/bid-loop 몽골유적", "재료 팩 여기 있으니 초안 써줘"
- **아닌 것**: 견적서·회사소개서·공문·입찰증빙 같은 **완성 서식**은 `vax-exit-kit`(하류)이 한다.

## 두 가지 실행 모습
- **대화형**: 사용자와 주고받으며 단계를 진행한다. 게이트마다 결과를 보여 주고 동의를 받는다.
- **루프형(`/bid-loop`)**: `loops/bid-loop/`의 절차 그대로 — **1회 호출 = 1스텝**, 첫 동작은 `_STATE.md` 읽기,
  끝나면 `_STATE.md` 갱신 후 즉시 종료. 헤드리스에서는 사용자 입력을 기다리지 않고 `차단사항`에 적고 끝낸다.
  (자세한 규칙은 `loops/bid-loop/bid-loop.md`. 이 SKILL.md는 단계의 **내용**을, bid-loop.md는 **운행 규칙**을 맡는다.)

## 절차 (순서를 바꾸지 않는다)

### P0 · 재료 팩 가져오기
1. 공고번호(예 `R26BK…`)를 받으면 Notion에서 입찰레이더의 그 공고 페이지를 찾고, 그 밑의
   **「📦 제안 재료 팩」** 자식 페이지를 읽는다(Notion MCP `notion-search` → `notion-fetch`).
2. 재료 팩이 없으면 멈추고 알린다 — "아직 재료 팩이 없습니다. 진행상태가 도전인지, 서버 재료 생성이
   돌았는지 확인해 주세요." **재료 없이 초안을 쓰지 않는다.** 사용자가 본문을 붙여넣으면 그것을 쓴다.
3. `references/material-pack.md`의 H2 열 개(0~9)가 다 있는지 본다. 빠진 항목은 알리고 뒤에서 `⚠️ 확인필요`로 다룬다.
   같은 자리의 **「📄 RFP 원문(추출)」** 자식 페이지도 연다 — P1 검산과 P4 인용의 원문이다. 두 페이지의 「판본:」 도장이 같아야 한다.
   원문 페이지를 사업 폴더에 `00_RFP원문_추출.md`로 저장해 두면 다음 스텝에서 Notion을 다시 읽지 않는다.
4. 사업 폴더가 없으면 `bids/{사업명}/`을 만들고 `loops/bid-loop/_STATE.template.md`를 `_STATE.md`로 복사한다.

### P1 · 평가표 검산
재료 팩 §0·§1·§2·§3·§4를 `01_평가표.md`로 옮긴다. **원문 표현 그대로**, 추측으로 채우지 않고 없는 항목은
`[RFP에 명시 없음]`. 기술:가격 비율, 정량·정성 배점표(항목·배점·만점 조건·증빙), 참가자격, 제안서 규격, 과업 산출물 개수.
**출구**: 정량·정성 배점 합이 100인지 검산. 안 맞으면 누락이니 재료 팩 §2를 다시 본다(서버 추출 오류면 `차단사항`에 적는다).

### P2 · 가점 진단 — 게이트 ①
정량 항목마다 재료 팩 §5(우리 자격·실적·인증)와 §6(정량 지표)을 대조해 실점을 센다. **단계별 점수표(신용등급 평점·실적 건수 구간·지체상금)는 재료 팩 §2 끝의 「원문 표」를 쓴다** — 표준표를 기억으로 쓰지 않는다(공고마다 다르다).
실적 건수형 항목은 색인 군집에서 기간·유형 조건에 맞는 실적을 **표로 세어** 보이고, 증명서 발급 가능한 공공기관 직접 계약을 먼저 센다(하도급은 예비). **근거가 없는 항목은
"확인필요"로 두고 0점으로 가정하지 않는다.** 실점을 **회복가능**(마감 전 서류로 0 가능 — 업종코드 등록, 확인서 갱신)과
**회복불가**(신용등급·매출·업력)로 나눈다. 회사 상수(신용등급·등록 업종코드·직생·설립일·특례 요건)는 **재료 팩 §5에서만** 읽는다 —
이 파일에 박지 않는다(갱신되면 재료 팩이 먼저 바뀐다).
**창업기업 특례는 P2의 선행 조건**이다. 공고에서 "창업기업·창업자·소기업" 조항을 확인하고, 불명확하면 발주기관 질의를 `차단사항`에 올리고 종료한다.
```
실점합계 ≤ 5.0                           → 통과 → P3
실점합계 > 5.0 AND 정성배점비중 ≥ 70%     → 사용자 판단 요청, 종료 (정성으로 역전 가능 — 자동 폐기 금지)
실점합계 > 5.0 AND 정성배점비중 < 70%     → 중단(가점미달). 실점 원인·회복가능 처리안 보고
회복가능 실점                              → 합계에 넣되 `차단사항`에 마감 역산 기한과 함께 등록
```
`02_가점진단.md` 서식: `| 정량항목 | 배점 | 우리 해당 | 획득 | 실점 | 구분 | 근거(재료 팩 §) |`

### P3 · 레퍼런스 확보
재료 팩 §5·§7과 `references/reference-index.template.md`의 색인 구조(기술요소 ↔ 실적 ↔ 재활용 문구)를 쓴다.
재료 팩에 §5·§7이 비어 있으면 위키 「레퍼런스 색인」(https://app.notion.com/p/3d16394f4c9981b493e3d4b5dc7884a9)을 Notion MCP로 직접 읽는다 — 이 페이지가 색인 정본이다.
과업을 기술요소로 분해 → 요소마다 실적을 매칭(발주기관·사업비·기간·역할) → 실적요건 충족 조합 명시 → **약점도 기록**
(`[레퍼런스 공백]`, 대체 근거를 R&D·특허·인력에서 찾고 없으면 공백으로 둔다).
**출구**: 매칭 3건 이상 AND 공백이 기술요소의 1/3 이하. 미달이면 다른 각도로 1회 재탐색, 2회 연속 미달은 보고 후 종료.
`03_레퍼런스매핑.md` 서식: `| 기술요소 | 매칭실적 | 발주기관 | 사업비 | 강점 문구(그대로 쓸 문장) |`

### P3.5 · 방향 → 전략 (서버 `bid_proposal_plan`에서 옮긴 판단)
`references/proposal-method.md`를 따른다. **돈 → 안 할 것 → 할 것 → 쓸 강점** 순서로 방향을 6~10줄로 잡고
**사용자 동의를 받은 뒤**, 배점 큰 항목 × 우리 강점으로 컨셉 한 줄·차별점 3개 이내·항목별 대응·리스크를 쓴다.
모든 주장 옆에 근거(재료 팩 §, 레퍼런스매핑 행)를 단다. 루프형이면 방향을 `_STATE.md`에 적고 다음 스텝에서 이어 간다.
**전략에 들어가기 전에 `references/distinctiveness.md` 규칙 1(이 발주처·이 과업·우리 실적의 고유 관찰 세 가지)을 먼저 채운다.**
고유 관찰 1(발주처 사정)은 **웹 조사로 확인한다**(한준 2026-09-04 "웹검색해서 pain point 공략"): 발주기관·해당 부서·사업의 최근 1~2년 기사, 기관 계획(로드맵·연차 목표), 관련 지자체·산업 사정을 검색해
**출처 링크와 함께** `03b_방향전략.md` §0 표에 적는다. 발주처가 RFP에 쓰지 않았지만 실제로 필요로 하는 것(예: 유학생 유치 → 언어 선택)이 여기서 나온다. 검색으로 확인되지 않은 추정은 적지 않는다.
컨셉은 그 세 관찰에서 나와야 한다 — 기술 이름에서 나온 컨셉, 다른 공고에 그대로 옮겨도 말이 되는 컨셉은 다시 쓴다(한준 2026-09-04: "AI로 쓰면 내용과 주장이 다 비슷해진다").
차별점 셋은 기술 · 수행 방식 · 사람과 인프라, 서로 다른 범주에서 하나씩 고른다(같은 파일 규칙 5).

### P4 · 초안 + 비판 검토 3회
목차는 발주처 지정 목차가 있으면 그대로, 없으면 **정성평가 항목 1개 = 챕터 1개**(위원이 채점표와 나란히 보게).
강점 나열이 아니라 **「RFP가 요구하는 것 → 우리 레퍼런스가 이미 해봤다는 증거」** 구조. 절마다 서술 문단과 슬라이드 요점을
함께 쓴다(나중에 자르면 문장이 끊긴다). 문체는 `references/house-style.md` 「쉬운판」과 **「대학생 강의처럼」**(꼭 필요한 전문용어만 그 용어로,
나머지는 아무 지식이 없는 제3자에게 알려 주듯 풀어 쓴다), 마무리에 `humanize-korean`.
장의 첫 문단은 우리 소개가 아니라 **발주처가 그 항목에서 겪을 문제**로 시작한다(`distinctiveness.md` 규칙 6).
투입인력 장은 `references/staffing-table.md`의 서식 구조에 위키 인력 데이터를 채운다 — 이름·이력은 재료 팩 §5-⑤와 위키에서만 가져온다.
초안은 마크다운(`04_제안서_v1.md`)으로 쓴다 — HTML·docx·pptx는 이것을 렌더한 결과다. docx가 필요하면 `doc-gen`으로 변환한다.
검토 3회는 관점을 **다르게** 둔다: ①누락(대응 없는 정성 항목·언급 안 된 산출물) ②증거(근거 없는 문장·"최적의" 같은 무근거 수식어)
③차별성(경쟁사도 쓸 수 있는 문장 → 우리만 쓸 수 있는 문장 — **`distinctiveness.md`의 점검표 7항목을 `logs/검토3.md`에 채운다.
회사명 가림 테스트를 통과하지 못한 문단이 하나라도 있으면 고친다**). 회차마다 `v{N+1}`을 새로 만들고 `logs/검토{N}.md`에 남긴다.
분량이 크면 챕터 단위로 쪼개고 `다음행동: P4-초안(3장부터)`처럼 재개 지점을 남긴다.

### P5 · 심사위원 채점 — 게이트 ②
`references/review-rubric.md`를 그대로 따른다. 페르소나 고정(심사 3회 이상·유사 제안서 20건 이상 검토한 위원, 작성자 시선 버림),
**감점 사유를 먼저 전부 쓴 뒤 점수**, 항목마다 **제안서 안 근거 위치(장·절) 인용 — 못 하면 0점**, 배점은 `01_평가표.md` 정성 배점을 100점 환산.
```
총점 ≥ 80                      → 통과 → P6
총점 < 80 AND 재작성횟수 == 0   → P4-재작성 (개선 우선순위 상위 3건만 겨냥. 전면 재작성 금지)
총점 < 80 AND 재작성횟수 == 1   → 중단(심사미달). 사람이 판단한다 — 무한루프 방지
```
80점은 합격선이 아니라 **착수선**이다. 통과 뒤에도 「질 수 있는 지점」은 P6에서 보강한다.

### P6 · HTML 디자인 1장 → Figma
초안 마크다운을 회사 디자인 토큰으로 렌더한다.
```bash
python3 scripts/render_html.py 04_제안서_v4.md 06_제안서.html "제안서 제목" --md-link 04_제안서_v4.md
```
- 색·모서리·글꼴을 새로 만들지 않는다(`scripts/ui_tokens.py`가 자동으로 들어간다).
- **공개 금지 정보가 있으면 렌더가 거부된다**(`references/guardrails.md`). 본문을 고친다. 우회하지 않는다.
- 필요하면 `frontend-design`으로 레이아웃 방향을 다듬고, `references/figma-handoff.md`대로 Figma에 넣는다.
  이 다음부터 **Figma가 정본**이고 세부 조정은 Claude-Figma로 한다. 슬라이드 덱이 따로 필요하면 5장 단위로 쪼개 진행한다.
- 회사 일반현황·조직·실적 장과 발표자료 톤은 `../../templates/company-intro/`의 회사소개서 마스터(v3)를 참고한다 —
  슬라이드 구조(일반현황 → 조직·인력 → 기술 → 실적 → 사례)와 「PROOF — 근거 한 줄」 표기법을 가져온다.
- **슬라이드 문법은 `references/figma-handoff.md` 「우리가 실제로 한 방식」을 따른다**(실측 3덱): 장 = PART 구분 슬라이드, 절 = 본문 1~3장,
  제목은 48~50px 주장 문장에 강조 낱말 1~2개, 하단 결론 바, 카드 3열·표·사진 카드 4열·숫자 대비 유형, 글꼴 Freesentation,
  **강조색은 발주처 CI 하나** + 무채색 단계(회사 토큰은 HTML 초안까지만).

### 스텝 종료 시 항상 (루프형)
`_STATE.md` 갱신(현재단계·다음행동·진행중:false·마지막갱신) → `logs/`에 1~5줄 → 사용자에게 3줄 보고
[완료한 것] [다음 스텝] [사람이 처리할 차단사항] → 종료. 다음 스텝을 이어서 하지 않는다.
스텝 진입 전 끝까지 갈 수 있을지 본다. 어렵다면 시작하지 말고 재개 지점만 더 잘게 적고 종료한다 — **반쯤 쓴 문서가 가장 비싼 실패다.**

## 원칙 (반드시 준수)
1. **단일 출처**: 회사명·대표·실적·인증·신용등급·업종코드·숫자는 재료 팩에서만. 임의 입력·추정·기억 인용 금지.
2. **근거 없는 문장은 쓰지 않는다**: `⚠️ 확인필요 — <무엇이 필요한지>`로 남긴다. 조용히 빈칸을 메우지 않는다.
3. **숫자·고유명사를 새로 만들지 않는다**: 재료 팩과 공고 원문에 있는 것만.
4. **게이트는 문서로 증명해야 통과**: 느낌으로 통과시키지 않는다. 채점은 루브릭 순서를 지킨 것만 쓴다.
5. **공개 금지 정보**(서버 주소·포트·모델명·채널 ID·내부 경로·토큰·임직원 실명)는 산출물에 넣지 않는다. 실명은 사람이 본다.
6. **방향 동의 후 진행**: P3.5 방향은 사용자 확인을 받고 전략으로 간다.
7. **초안은 초안이다**: 사람이 Figma·노션에서 고친 값이 정답이다. 되돌려 덮어쓰지 않는다.
